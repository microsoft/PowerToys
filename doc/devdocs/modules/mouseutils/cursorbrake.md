# CursorBrake

CursorBrake adds resistance where two monitors meet. The cursor stops at an edge shared by two monitors until the user pushes past it for a set distance, so a fast move toward a target near the edge (a scrollbar, a close button, a taskbar, a browser tab) does not overshoot onto the next monitor. Holding the configured cross key (Ctrl by default, or Shift) crosses freely. A braked edge yields to a long enough push. A wall yields only to the cross key and the bypasses below.

## Behavior

- **Inner edges only.** An edge counts when two monitors share it. Outer edges, gaps between monitors and single-monitor setups are left to Windows, including its own corner and dead-zone easing. The one exception is a monitor with a wall out (below).
- **Push-through.** A move that would land on another monitor across an inner edge is held just inside the source monitor, and its overshoot perpendicular to the edge adds to a push. When the push reaches the threshold, the move crosses and the push resets.
- **DPI scaling.** The threshold is `push_distance * sourceDpi / 96`, using the DPI of the monitor the cursor leaves. Windows moves relative input about `sourceDpi / 96` pixels per mouse count, so the hand travel to cross is the same in both directions across a mixed-DPI edge.
- **Move cap.** Each event adds at most 10 logical pixels (scaled the same way) to the push, so a fling or a shake holds at the edge instead of crossing in one or two events.
- **Moving away drains.** The component of a move away from the pushed edge comes off the push, floored at 0. A move along the edge costs nothing. The push belongs to the source monitor and the crossed side, so a hard push into a corner that lands on two neighbors in turn keeps adding up.
- **Free return.** With the setting on, the cursor can cross straight back over the edge it just crossed with no push. The allowance ends 100 logical pixels from that edge, on another crossing, or on a bypassed move.
- **Cursor clip.** When an app confines the cursor with `ClipCursor`, as a full-screen game does, Windows clamps every move into the clip after the low-level hook, which still sees the unclamped point. The engine judges each move between the clamped points, so a clip on one monitor never holds the cursor, and a clip spanning an edge brakes it as usual. With no app's clip, `GetClipCursor` reports the virtual screen's bounding rect, so a move past an outer edge is judged where that rect puts it: a diagonal at an inner corner holds, and an excursion along an outer edge keeps the push. The push and the free return start over when the clip starts or stops letting the cursor through where they lead, as when a game confines or releases the cursor. A failed `GetClipCursor` keeps the last clip.
- **Bypass.** Holding the configured cross key (`cross_modifier`: Ctrl or Shift, never both), or holding a mouse button while "Disable resistance while dragging" is on, crosses freely and resets the push and the free return.
- **Input classification.** Pen and touch input passes. In a remote session the module stands down entirely. Injected input passes, unless `dwExtraInfo` carries the test marker `0x4342524B` and Windows does not flag it as injected from a lower integrity level (`LLMHF_LOWER_IL_INJECTED`). The module brakes such a move like hardware so scripted tests can drive it.
- **Display changes.** The monitor layout is rebuilt on `WM_DISPLAYCHANGE`, `WM_SETTINGCHANGE` with `SPI_SETWORKAREA`, and `WM_DEVICECHANGE`, debounced by 500 ms. A layout or settings change resets all push and free-return state.

## Per-edge settings

Each direction across an edge has a rule: Custom with a push distance, Off, or Wall. The `edges` setting names pairs of monitors by ID and sets the rule for both directions, or with `one_way` for the first-to-second direction only.

- **Lookup.** `RuleFor` decides every crossing's rule, in this order: a one-way entry from the source to the neighbor, a both-ways entry naming the two in either order, then the default. The default is Custom at `push_distance` when `edge_filter` brakes the side's axis, and Off when it does not. The first matching entry wins. `RuleFor` is the only place a rule is decided, so a rule for every way out of one monitor belongs in front of the entries there.
- **Neighbor.** `RuleAt` finds the monitor across the crossed side: the destination when it shares that side, otherwise the monitor across the side at the proposed point's coordinate along it, clamped into the source's span. For a move through a corner that is the corner pixel. With no neighbor, the default applies.
- **Corners.** A destination that meets the source only at a corner borders neither side the move passes, so the move meets both sides' rules at the corner pixel and takes the stricter (`Stricter`): Wall first, then the larger push distance, then Off. The default ranks as Custom at the global distance. A wall on either side therefore holds the corner, and a monitor walled on every side it shares cannot be left through one. No entry can name a corner-only pair, because `ResolveEdges` keeps only pairs that share an edge.
- **Custom** brakes as above with the entry's distance, scaled by the source DPI. **Off** is never offered by `CrossedSide`, so the move goes through and no free return opens, as for a filtered edge. **Wall** holds without adding to the push and never crosses. Leaning on a wall banks nothing for a braked neighbor on the same side.
- **Gaps beside a wall.** A move whose point lies on no monitor, in a gap or past an outer edge, is left to Windows, which does not put it on the nearest monitor. In a guest with a gap beside a monitor's right side, a move 10 px into the gap stayed on the source near one corner and jumped 278 px onto a walled neighbor elsewhere. So when the source has a wall out to any monitor sharing an edge with it (`HasWallOut`, by the rule `RuleFor` decides, one-way entries included), such a move is held on the source's last pixel. A monitor walled on every side therefore can be left only with the cross key, as the overlay and the trap caution say. Without a wall out, the move goes to Windows.
- **Free return** is checked against the way back when it is used, with the rule the crossing meets, through a corner the stricter one. When that rule is Wall, the free return is dropped and the move is judged as any other.
- **Bypasses pass walls.** The cross key, absolute input, a remote session and a drag with "Disable resistance while dragging" on all cross.
- **Without entries** every lookup reaches the default, whose Off is exactly the filter's test, so the engine decides as the filter alone does, move for move. `CursorBrake.UnitTests` holds the equivalences.

### Monitor identity

`RebuildLayout` takes the geometry from `EnumDisplayMonitors` on the per-monitor-aware hook thread, so the rects are physical, and the new geometry applies at once. The identities, names and numbers are read on a thread-pool work item (`IdentityReader`), because `GetDisplays` and `QueryDisplayConfig` can stall during a display change and the hook thread must keep answering mouse input. The reader posts `WM_APP + 3` when a read finishes, a failed one included, and `ApplyIdentities` takes the result on the hook thread (`JudgeIdentities`). It drops a read for an older layout. `WM_DISPLAYCHANGE` advances the layout's generation before the debounced rebuild, so a read still running for the replaced layout is dropped too. A read that failed, or whose monitors do not show the GDI device and rect the layout holds when it finishes, leaves the identities as they are and is read again. Otherwise it applies, resolves the entries again and publishes. Until the read arrives, a monitor that kept its GDI device and rect keeps what was read for it (`MatchPrevious`), and any other monitor has no ID. Each monitor's ID comes from `DisplayUtils::GetDisplays`, matched by `HMONITOR`, in PowerDisplay's `Monitor.Id` form, `\\?\DISPLAY#<EDID code>#<instance>`. Its friendly name comes from `QueryDisplayConfig` and `DisplayConfigGetDeviceInfo` (`DisplayNames.cpp`), matched to the device interface path. Its number is the one Windows Settings shows: Settings numbers every available display target, active or not, by adapter and then by target id, so a monitor detached from the desktop keeps its number (`DisplayNumbers`, from `QueryDisplayConfig(QDC_ALL_PATHS)`). Each monitor's target is the first active path showing its GDI device. A monitor without a target numbers after every target. The same path's output technology marks a built-in panel (internal, embedded DisplayPort or embedded UDI). A monitor without an instance keeps its geometry and has no ID: its edges are published and brake at Default, and no entry reaches them. When a read fails or does not match the layout, `GetDisplays` reports a failure, or a monitor has no ID, the identity is read again up to three times, a second apart, on the window timer. Each read logs how long `GetDisplays` took, and logs the EDID code but never the instance.

IDs compare without regard to ASCII case on both sides, and only ASCII letters fold, since device paths are ASCII: `SameMonitorId` in C++, `CursorBrakeEdgeModel.IsSameId` in C#.

### From settings to the hook

`set_config` runs on the runner thread. `ReadEdgesSetting` (`EdgeSettings.cpp`) parses the list into ID-named overrides, skipping each bad entry alone: an entry that is not an object, without two distinct non-empty IDs of at most 512 characters, with a mode other than 0, 1 or 2, with a `one_way` that is not a bool, or with a `push_distance` that is not a finite number. Only the first 256 elements are read, and distances are clamped like the global one. A missing `edges` key means no entries. A value that is not a list keeps the previous entries.

The parsed list waits in a mutex-guarded slot, and `set_config` posts `WM_APP + 1` to the hook thread's window. The window procedure takes the list and `ResolveEdges` turns it into `Layout::edges` against the current monitors: an entry applies only while both its monitors are connected and share an edge. It resolves again after every rebuild. The hook callback never locks and never allocates. A change to `Layout::edges` resets the push and the free return, like any layout change.

### detected-edges.json

The module writes `%LOCALAPPDATA%\Microsoft\PowerToys\CursorBrake\detected-edges.json` on start, after every layout rebuild and after every settings apply that changes the entries. The write runs on a thread-pool work item (`EdgePublisher`), since disk I/O must not stall the hook thread. Only the newest snapshot is written, one write at a time.

| Key | Content |
| --- | --- |
| `version` | `1` |
| `identified` | Whether every monitor has an ID |
| `monitors` | `id` (empty without one), `name`, `rect` (physical, left, top, right, bottom, half-open), `dpi`, `primary`, `number` (Windows' display number), `built_in` |
| `edges` | `InnerEdges` output: `monitors` (indices), `axis` (`vertical` for side by side along x = `at`, `horizontal` for stacked along y = `at`), `from`, `to` |
| `seen` | `monitors` (two IDs) and `last_seen_utc` (ISO 8601) for each pair seen next to each other within 180 days |
| `expired` | `monitors` (two IDs) for each pair whose 180 days ran out while an entry still names it |

The module owns every timestamp. Each write stamps the pairs that shared an edge before or after the change with the current time, and adds a pair that only an entry names at the current time, once: a pair already in `seen` or `expired` is not added again, so naming a pair never extends its retention. A pair last seen more than 180 days ago leaves `seen`, and moves to `expired` while an entry names it. It leaves `expired` when no entry names it any more or when the two monitors are seen together again (`MergeSeen`). A clock more than a day behind the newest `seen` stamp is wrong, as after a firmware reset or a restored checkpoint: that write drops and expires nothing, and stamps with the newest stamp instead of the clock, so a pair keeps its entries until the clock is right again. A clock that runs more than 180 days ahead still expires every pair not seen meanwhile, since nothing tells it from the right time. Each write keeps at most 1024 `seen` pairs: every present and named pair, then the most recently seen of the rest. Reading the file back, the module keeps a stamp ahead of the clock, skips a stamp at or past 2100-01-01 and an ID longer than 512 characters, and reads at most 1024 elements of each list. A file edited to hide a named pair's stamp past the 1024th element gives that pair one fresh 180 days, since the module never reads the stamp. Settings watches the file with `Helper.GetFileWatcher`. It ignores a read that fails, since the write's own change notice follows, and removes every entry whose pair is missing from `seen`. It saves only when that removed something, so loading the page never rewrites `settings.json`.

### Show on screens

The `show_edges` custom action posts `WM_APP + 2` to the hook thread. The window is a findable top-level window, so another process can post the same message. A `ShowGate` lets a message through only when `call_custom_action` asked for it, and at most once a second, so a stream of posts cannot make the hook thread tear down and rebuild the overlay. The hook thread copies the layout, the rules and the display numbers into `EdgeOverlay`. The overlay runs on a short-lived thread of its own: one layered, click-through, topmost window per display, with a strip for each direction on the display it leaves, a label for its rule, and the display's number. A display that can only be left with the cross key also shows "Hold Ctrl to leave", with the configured key. The overlay's strings live in the module's `Resources.resx`, which `tools\build\convert-resx-to-rc.ps1` turns into the string table at build time, so they are localized like the other native modules' strings. The overlay closes after 5 seconds, on Esc or a mouse click, or on a display change, and `disable()` closes it and waits for its thread.

## Architecture

CursorBrake is a native C++ in-process module (`PowerToys.CursorBrake.dll`), like the other passive Mouse Utilities.

- `CursorBrakeCore.h` holds the decisions as a header-only, Win32-free `cursorbrake::Engine`. Its input is the monitor rects with their DPI, the current and proposed points, the input kind, and the modifier and button state. Its output is `Allow` or `Hold` with the point to place the cursor at. It is deterministic, which is what lets `CursorBrake.UnitTests` and `CursorBrake.FuzzTests` drive it directly.
- `dllmain.cpp` implements `PowertoyModuleIface`. `enable()` starts a dedicated thread that installs `WH_MOUSE_LL` and pumps messages, since low-level hook callbacks are delivered to the installing thread. `disable()` signals a terminate event and joins the thread.
- The hook handles `WM_MOUSEMOVE` only. It classifies the event (`ClassifyInput`), reads the current point with `GetCursorPos`, the cursor clip with `GetClipCursor`, and the modifier and buttons with `GetAsyncKeyState`, and asks the engine. On `Hold` it calls `SetCursorPos` and returns `1`. `SetCursorPos` raises no low-level hook event, so the module never sees its own correction.
- A hidden top-level window on the hook thread receives the display, device and session-change broadcasts. A message-only window does not receive those broadcasts.
- The hook path does not log, per `.github/copilot-instructions.md`. Settings, layout and session changes log through the `cursor-brake` logger.

## Settings

Stored at `%LOCALAPPDATA%\Microsoft\PowerToys\CursorBrake\settings.json`. The snake_case keys must match between the C# `CursorBrakeProperties` and the C++ `parse_settings`.

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `push_distance` | int | `300` | Strength: how far to push past an edge before crossing, in logical pixels. Clamped to 0-1000; 0 turns resistance off |
| `free_return` | bool | `true` | One free crossing straight back over the edge just crossed |
| `edge_filter` | int | `0` | Apply to: 0 all edges between monitors, 1 side-by-side only, 2 stacked only |
| `disable_while_dragging` | bool | `false` | Cross freely while any mouse button is held |
| `cross_modifier` | int | `0` | Cross freely while holding: 0 Ctrl, 1 Shift |
| `edges` | list | `[]` | Per-edge entries: `monitors` (two IDs), `one_way` (left out when false), `mode` (0 Custom, 1 Off, 2 Wall), `push_distance` (kept under Off and Wall). See Per-edge settings |

`parse_settings` keeps the previous value for a non-finite number, an out-of-range choice, or a key of the wrong type. The module on/off state lives in `EnabledModules.CursorBrake` in the global settings. There is no activation hotkey: the brake is on whenever the module is.

## Settings UI

CursorBrake is a section on the shared **Settings > Mouse utilities** page (`MouseUtilsPage.xaml`, bound to `MouseUtilsViewModel`), first in the page's alphabetical order. The enable toggle is its own card. Everything else lives in a "Resistance and behavior" expander that is disabled until the module is on.

| Control | Type (UI range) | Setting key | ViewModel property | Default |
| --- | --- | --- | --- | --- |
| CursorBrake | toggle | `EnabledModules.CursorBrake` | `IsCursorBrakeEnabled` | off |
| Strength | slider (0-1000, 25 px steps; the thumb tooltip shows the value) | `push_distance` | `CursorBrakePushDistance` | 300 |
| Free return | checkbox | `free_return` | `CursorBrakeFreeReturn` | on |
| Apply to | combo box | `edge_filter` | `CursorBrakeEdgeFilter` | All edges between monitors |
| Disable resistance while dragging | checkbox | `disable_while_dragging` | `CursorBrakeDisableWhileDragging` | off |
| Cross freely while | combo box | `cross_modifier` | `CursorBrakeCrossModifier` | Holding Ctrl |

A second expander, "Edges between monitors", holds the edge editor (`CursorBrakeEdgesViewModel`, exposed as `MouseUtilsViewModel.CursorBrakeEdges`). It shows a map of the displays as a key, with a lettered badge per edge, and one row per edge as the editor. A row's combo box offers Default, Custom, Off, Wall and "Different each way", which adds a row per direction. Settings writes one both-ways entry when both directions agree, otherwise one one-way entry per direction that is not Default, and Default deletes the pair's entries (`CursorBrakeEdgeModel`). The editor shows Windows' display numbers, which the module publishes per monitor in `detected-edges.json` (`number`, with `built_in` for a built-in panel). A stock Informational InfoBar names a display whose every way out is a wall while some way in is not, counting the ways through a corner as the module judges them. The editor shows what the module does, so it loads the entries as the module reads them (`CursorBrakeEdgesConverter` and `CursorBrakeEdgeModel.Sanitize`): the first 256 elements, without null entries, entries without exactly two IDs, null IDs, IDs longer than 512 characters and entries with a field of the wrong type, and with each distance clamped into 0 to 1000. A field given twice is judged by its last copy, as the module's parser keeps it, and unknown fields are passed over. A wrong-typed field therefore drops its entry alone and never fails the whole settings file. So does an ID holding a lone surrogate, which .NET cannot decode and no monitor carries. Two shapes still differ from the module, and both need a hand edit. A number past double's range, such as `1e400`, drops its entry in Settings, while the module's parser rejects the whole file and keeps its previous settings until Settings next saves the file without it. Nesting deeper than the serializer's limit of 64 fails the whole file in Settings, which then saves the defaults, because the serializer's reader stops before the converter can pass over the field. It reads `detected-edges.json` with null lists as empty (`Clean`), and a failure to show the file leaves the editor empty rather than ending Settings. Entries for monitors that are not connected show under "Disconnected monitors" with Forget and the date Settings removes them, 180 days after the pair was last seen together. "Show on screens" sends the `show_edges` custom action.

When the page loads, the ViewModel repairs nulls and out-of-range values from a hand-edited file to the defaults and the module's ranges, in the settings object it saves. The controls therefore show what the next save writes and sends. Until that save, the module ignores an out-of-range choice and keeps its last valid one, and it clamps an out-of-range distance the same way the ViewModel does. The group is GPO-aware through `ConfigureEnabledUtilityCursorBrake`: when policy forces the module on or off, the toggle is disabled and a `GPOInfoControl` warning shows. UI tests find controls by automation id: `MouseUtils_CursorBrakeTestId` (group), `MouseUtils_CursorBrakeToggleId`, `MouseUtils_CursorBrakeOptionsId`, `MouseUtils_CursorBrakePushDistanceId`, `MouseUtils_CursorBrakeFreeReturnId`, `MouseUtils_CursorBrakeEdgeFilterId`, `MouseUtils_CursorBrakeDisableWhileDraggingId` and `MouseUtils_CursorBrakeCrossModifierId`.

## Building and debugging

- Native module only: `msbuild src/modules/MouseUtils/CursorBrake/CursorBrake.vcxproj /p:Platform=x64 /p:Configuration=Release`. The DLL lands in `x64\<Config>\PowerToys.CursorBrake.dll`, where the runner loads it from (`knownModules` in `src/runner/main.cpp`).
- Without the runner: `tools\module_loader` loads the DLL with a `settings.json` beside it (`ModuleLoader.exe PowerToys.CursorBrake.dll`). Exit any running PowerToys first, since two CursorBrake hooks would both brake.
- Debugging: the hook runs inside the runner, so attach to `PowerToys.exe` and break in `dllmain.cpp`. A breakpoint inside `HandleMove` stalls system-wide mouse input and risks `LowLevelHooksTimeout` removing the hook; break in `CursorBrakeCore.h` from the unit tests instead.
- Inner-edge behavior needs two or more displays: multi-monitor hardware, or a guest with several virtual displays. In either, `SendInput` moves carrying the test marker exercise the brake from a script.

## Testing

- `CursorBrake.UnitTests`: table-driven CppUnitTest cases over synthetic layouts (side by side, stacked, partial overlap, mixed DPI, single monitor, four-monitor junction) covering push accumulation, draining, the move cap, DPI scaling, the direction filter, modifiers, dragging, free return, the cursor clip and settings or layout resets. `EdgeTests.cpp` covers the per-edge helpers, the settings parser and the detected-edges file, and the engine tests cover rules, walls, one-way values and the equivalences with no entries.
- `Settings.UI.UnitTests`: `CursorBrakeEdgeModelTests` (lookup, normalization, pruning, the trap check, numbering) and `ViewModelTests\CursorBrakeEdges` (rows from a fixture file, edits, splitting, pruning, file robustness) on a mock file system.
- `CursorBrake.FuzzTests`: a libFuzzer target over the engine, with clips set and lifted between moves, including empty and inverted ones. Invariants: a `Hold` point is always inside the source monitor, only a move that lands on another monitor once clamped into the clip, or on no monitor from a source with a wall out, is held, `Allow` never alters the point, and no input crashes. Layouts carry random per-edge entries, and further invariants hold: no move crosses a shared edge whose rule in that direction is Wall without a bypass, no move leaves through a corner where either side is Wall without a bypass, no move leaves a source with a wall out for no monitor without a bypass, and spelled-out forms of the same rules (explicit defaults, one-way pairs for a both-ways entry, Off entries for the filter) decide every move alike. It builds to `x64\Release\tests\CursorBrake.FuzzTests\`, which the OneFuzz pipeline's `**/tests/*.FuzzTests/**` glob picks up.
- `MouseUtils.UITests.Next/CursorBrakeSettingsTests.cs`: the options follow the enable toggle, every setting persists across a restart, and marked moves within one monitor land where they were sent. CI agents have one monitor, so inner-edge behavior needs multi-monitor hardware or a guest with several virtual displays. Before moving, the no-op case waits for a fresh `CursorBrake hook installed.` line in the module log. It fails on `Failed to install CursorBrake mouse hook`, and reports inconclusive when the session line before the install says the session is remote.

## Known limitations

- **Elevated windows.** The runner is medium integrity, so UIPI keeps its low-level hook from seeing input over a window running as administrator. The brake does not apply there unless PowerToys runs as administrator.
- **Injected relative input.** Gamepad mappers, scripts and Mouse Without Borders relative mode inject their moves, so they pass unbraked.
