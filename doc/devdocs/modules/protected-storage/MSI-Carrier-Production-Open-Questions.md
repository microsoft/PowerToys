## 一、已明确的前提，不再重复提问

| 事项 | 本文采用的前提 |
|---|---|
| 业务数据 validation | 由对应 module 负责，包括格式、转换及业务语义；通用 runtime/storage service 不实现各模块的业务规则 |
| 迁移阶段的信任假设 | 按本次明确意见，承担迁移 validation 的 PowerToys/module 在该阶段尚未被攻击者控制 |
| 后续 writer 的信任边界 | 保存时校验 caller 身份和 owner/目标写权限；不额外识别已经通过认证的 caller 是否被攻陷，不承诺其提交内容在被攻陷后仍安全（Q01 已决） |
| 更新载体 | Bootstrap 和 Runtime 的发布字节均来自对应版本 MSI，不再单独发布绕过 MSI 的 runtime bundle |
| 身份与实例 | MSI 注册属于真实用户，不属于 VA；SCM 注册是机器级资源，但实例、VA 和 Code/Data 按 owner SID 隔离 |
| 常规实例更新 | 沿用已有授权边界，由 VA 更新自身 Bootstrap/Runtime；不为每次常规代码更新再次请求 UAC |
| 多用户更新策略 | 各 owner 的实例独立更新，不因 A 更新而连带更新 B；安全更新也不设强制完成期限或全用户强推机制（Q03 已决） |

### 对迁移假设的准确解释

这个前提允许业务 validation 与通用存储服务解耦，但需要按下面的边界实现：

```text
module 读取旧数据，取得稳定快照
→ module 对该快照执行业务 validation / 必要的转换
→ 将通过验证的同一份输出字节交给 service
→ service 按授权目标原子提交并记录初始化状态
```

“module 可信”**不等于旧文件可信**；旧文件仍可能已被修改，必须交由 module 校验。
可信窗口需要覆盖本次 validation、移交和提交，不能只信任某一个校验瞬间，
然后让 service 重新按原路径读取一份已经可能变化的文件。

service 不理解模块业务，并不意味着它不做安全检查。以下属于通用机制，仍是必需项：
调用者/owner/目标授权、不可伪造的目标绑定、大小与资源限制、并发条件、
原子提交、初始化状态保护，以及更新代码的签名/哈希/版本检查。
`IfAbsent` 只是写入条件，不是授权；迁移成功后也不能因受保护文件缺失就自动重新导入旧文件。

这些是实现约束，不要求你逐项选择 API、算法或存储格式。

## Q01：迁移后的安全承诺覆盖到哪里？（已决定：A）

**2026-09-22 评审结论：采用 A，按受信任 writer 模型推进。**

原比较的两种承诺：

| 选择 | 产品承诺 |
|---|---|
| A：受信任 writer 模型 | 阻止直接文件篡改和未授权客户端写入；每次被接受的业务校验/授权写入都信任相应 module。若该 module 已被完全控制，不承诺其合法写接口提交的内容仍安全 |
| B：后续普通 module 被注入也在范围内 | 迁移采用本次可信假设，但后续高权限行为还必须有一个未被该攻击控制的业务授权边界，或在高权限使用端实施最终授权 |

本期范围：

- 保存阶段仍校验 caller 身份，以及 owner、目标和具体写权限；未经授权的客户端不能绕过这些检查。
- 对已经通过认证的合法 caller，不再额外尝试证明它的运行态是否被注入或攻陷。
- module 继续负责业务 validation，通用 runtime/storage service 不承担模块业务规则。
- 不为覆盖“合法 caller 被攻陷”而新增受保护业务审批组件、内容预授权协议或额外的保存/启动 UAC。
- 保留现有执行侧规则和 Windows 提权确认，由授权管理员对实际的提升请求作判断。

决策依据：目前没有已经证明通用、可靠且成本低的运行态失陷识别方案，
不以此扩展本期架构或阻塞落地。将来若有具体、低成本且可验证的方案，再单独评估。

安全声明必须与这个选择一致：保护的是直接文件篡改与未授权写入，
**不承诺合法 writer 已被控制后，其合法接口提交的内容仍符合用户意图。**
同一个用户 SID 不自动等于合法 module；签名/路径正常也不能证明进程未被注入。
UAC 不替产品核对 Workspace 计划 P 与 Q 的一致性，也不保证管理员一定能发现被替换的目标或参数；
这是接受相应剩余风险，不是把 UAC 当作解决该风险的技术证明。

本决定不替 Q05 预先决定具体迁移规则，也不取消已有的业务 validation、
调用授权、跨用户隔离或代码更新验证。最终安全评审仍须按上述明确范围评估。

评审结论：**A 已确认；Q01 关闭，不追加运行态失陷识别要求。**

## Q02：无法取得管理员权限时怎么办？（暂定阻断，待 PM 确认）

**2026-09-22 评审进展：核心是保护边界建不起来时，允许降级还是阻断。当前倾向 block users，不允许不安全降级，仍需与 PM 沟通。**

暂按以下范围记录，尚不作为最终产品批准：

- 首次预配需要管理员授权，而用户取消或无法提供时，不允许通过旧的普通用户可写路径继续使用依赖 protected store 的功能。
- 对 Workspaces，阻断相应的保存/启动路径，展示需要完成安全设置的原因，并提供重新授权/重试入口。
- 保留旧文件供后续正常迁移，不因无法预配就删用户数据；旧文件不能作为绕过保护的活动数据源。
- “阻断”暂按受影响的功能理解，不直接扩大为禁止安装或启动整个 PowerToys。不依赖该保护边界的功能可以继续使用，具体范围和文案待 PM 确认。
- **普通用户身份本身不是阻断条件。** 如果其服务和 protected store 已正确预配且可用，后续正常使用和已有实例的常规更新不要求再次取得管理员权限。

### 仍待确认：授权触发时机

当前 Demo 已使用首次管理员授权，但生产产品何时发起这次授权尚未由本次讨论决定：

| 选择 | 影响 |
|---|---|
| 安装 PowerToys 时就要求服务预配完成 | per-user 安装也可能因此新增管理员授权要求；无法授权的用户可能被挡在安装阶段 |
| 首次启用 Workspaces 等受保护功能时预配 | 可以继续安装/使用其他 PowerToys 功能；受保护功能在服务准备好之前不可用 |

**建议：采用第二种。** per-machine 主安装已有授权、且真实 owner 明确时，可以顺带预配该 owner，
减少重复提示；不能把它理解为未来所有用户都已预配。

待 PM 确认：是否正式采用上述 fail-closed 策略、阻断哪些功能，以及安装/首次启用时的提示和重试体验。

“标准用户无管理员凭据、机器上也没有已有授权基础设施，却能自行创建 SCM 服务”
不能作为这个方案的默认承诺。

## Q03：多用户更新范围与时序（已决定：独立更新，无强制期限）

**2026-09-23 评审结论：普通更新互不影响；PowerToys 作为 consumer app，安全更新目前也没有强制完成期限，本方案不额外引入强制用户更新机制。**

这里问的是“更新谁、何时触发”，不是服务被占用或无法关闭时怎么处理。
原文的“立即完成”容易混淆，改为以下正常目标时序：

```text
A 发起其 PowerToys 更新
→ 将 A 的已有服务实例纳入本轮更新协调
→ B 的服务、数据及 carrier MSI 注册不随之被更新
```

“纳入本轮”不意味着零停机、没有等待或保证每次都能立刻成功。
运行中的服务可以通过维护协调、停止、替换和重启完成升级；
若确实停不下来、文件被锁定或更新失败，重试、提示、功能可用性及修复流程由 Q04/Q08 决定，
不因本项关闭而预先决定那些失败策略。

更新范围与期限：

- 允许不同用户的服务实例保持不同版本，不设全机同步完成时限。
- B 在自己的正常用户流程中协调所需版本；“下一次启动新版 PowerToys 时检查兼容性”仍是集成建议，不是强制更新倒计时。
- 安全更新沿用 consumer 产品策略：不新增强制完成期限，不引入因“逾期未升级”而停用实例的机制。
- 不要求 SYSTEM 部署一次性升级所有离线用户，也不把 SYSTEM 身份当成真实 owner 的 per-user MSI 上下文。
- 不强制更新不等于跳过代码验证或版本兼容检查；实际不兼容/不可用时的行为仍由 Q04 定义。

“互不影响”针对各 owner 的服务实例、数据和 carrier MSI。
**per-machine PowerToys 主程序文件本来就是共享的**，其机器级升级不能被描述为 A/B 各自保留独立的主程序版本；
主程序与各 owner 服务之间的兼容协调仍必须实现。

评审结论：**Q03 的更新范围和期限政策已确认，关闭；具体集成与异常处理不宣称已经验证完成。**

## Q04：失败隔离与重试（已决定：不影响其他模块，重试失败操作）

**2026-09-23 评审结论：不影响其他正常模块，但失败模块必须有重试机制（Retry the failed operation）。**

产品行为：

- 主 PowerToys 更新成功后，不因某个模块的服务更新/初始化失败而连带回滚主程序或阻断其他正常模块。
- 失败模块明确显示失败原因和待恢复状态，并提供重试失败操作的入口；不能只留一条日志让用户自行重装。
- 重试作用于相应 owner 和失败的操作/维护单元，不重做已经成功的其他用户或模块操作。
- 依赖尚未恢复时，不把失败操作报告为成功，也不通过不受保护的旧路径绕过失败。

实现约束：

- 重试前查询实际状态，按持久化事务和幂等规则恢复；“重试失败操作”不等于盲目重放最后一条命令。
- 如果失败单元是 carrier MSI 事务，可以按其事务边界重试该 owner 的 MSI 维护，而不是从任意 custom action 中间跳入。
- 对“VA 已提交、MSI 状态未完成”的情况，需要协调一致性，不能为了重试而无条件回退已提交版本。
- 重试不能跳过 caller、目标、签名或数据校验，也不能重复产生成功提交的副作用。
- 是否加入后台自动重试、触发时机、次数和退避属于后续实现细节；本次不承诺无限自动重试。
- 若失败的根因需要管理员修复或重启，沿用相应授权与 Q08 的恢复边界，不靠重试绕过。

如果将来多个模块共享同一服务，工程实现须按真实依赖关系限制失败影响，
不能让一个模块的独立失败扩散为全局失败，也不能把共享依赖实际不可用的模块标为正常。

评审结论：**失败隔离及 Retry the failed operation 已确认；Q04 关闭，重试机制尚待实现和验证。**

## Q05：迁移失败与敏感字段怎么处理？（已决定）

**2026-09-23 评审结论：不允许部分迁移、敏感行为由 module 决定、目标初始化及防重复覆盖语义、成功后 protected store 为权威源，均已确认。**

| 情况 | 已确认决定 |
|---|---|
| 文件损坏、版本不识别或其他迁移错误 | **不允许部分迁移。** 本次迁移单元整体失败，保留原文件、说明原因，不发布部分结果或成功标记；原因解决后重试 |
| 旧配置包含高权限启动等敏感行为 | **由 module 验证，并由 module 决定是否需要迁移。** 通用 service 不制定业务规则，也不替 module 过滤、批准或兜底 |
| 目标已经初始化 | 下文解释：已有成功提交的目标数据，不能被再次自动迁入的旧副本覆盖；这不禁止正常编辑/保存 |
| 迁移成功 | **已确认。** protected store 成为唯一权威来源，不再作为自动 fallback 使用旧文件；旧源文件是立即删除还是备份，按 Q07 确定 |

“不允许部分迁移”指不能遇到错误就跳过坏条目、把剩余内容当成迁移成功。
module 可以按其明确的业务迁移规则构造完整目标结果，或拒绝迁移；
最终接受的迁移单元必须完整验证后整体提交，不能留下半份已生效状态。
这不要求把所有模块绑成一个全局迁移事务，也不让一个模块失败阻断其他正常模块（Q04）。

### “目标已经初始化”是什么意思？

“目标”是某个 owner、某个 module 的受保护数据目标，例如“用户 A 的 Workspaces 配置”。
“已初始化”表示它已经完成过首次有效数据的提交，并具有一致的受保护初始化状态。

| 状态 | 是否属于 Workspaces 目标已初始化？ |
|---|---|
| MSI/服务安装成功，Code/Data 根目录建好，但 Workspaces 数据尚未提交 | 否；基础设施就绪不等于模块数据初始化 |
| 旧 Workspaces 配置已验证并完整提交至 protected store | 是 |
| 没有旧数据，module 已合法创建初始设置，例如空工作区列表 | 是；合法空数据不是“从未初始化” |
| 记录表明已初始化，但目标文件后来损坏或丢失 | 属于异常/恢复场景，不能自动当作未初始化，再读取旧文件覆盖 |

例如：A 第一次迁移成功后，又在新版里编辑了 Workspace。
之后重启、升级或重试时，如果再次读取旧路径中的老副本进行初始化，
就可能覆盖 A 的新设置，甚至把后来被修改过的旧文件重新引入。
这里的“已初始化不覆盖”就是防止这种重复自动迁移。

判断按 owner/module/目标分别进行：A 已初始化不代表 B 已初始化，
Workspaces 已初始化也不代表其他模块已初始化。
检查初始化条件与提交需要在 service 内原子完成，避免两个客户端同时迁移时相互覆盖。

**这不把 protected store 变成永久只读。** 后续正常编辑/保存仍走已授权的普通写入流程；
业务 schema 升级或用户显式导入，也不是重新执行这条“首次从旧路径初始化”的流程。

评审结论：**首次有效提交才算目标初始化；合法空数据也算已初始化，后续不再自动导入旧副本，正常编辑/保存不受此限制。Q05 已确认并关闭，迁移机制仍待实现与验证。**

## Q06：全机卸载范围（已决定：尽量清理全部，残留不阻塞方案）

**2026-09-23 评审结论：全机卸载时尽量卸载所有产品服务；若因用户离线等实际限制无法删除部分项目，不应成为此 solution 的 blocker。**

产品目标：

- 对已确认属于本产品的全部用户实例执行适用的清理，而不只清理触发卸载的当前用户。
- 正常条件下尽量停止、移除产品服务和运行组件，并通过正确的维护机制处理对应安装注册。
- 不要求一次全机卸载必须清掉所有离线用户的所有资源，才能接受这套架构或交付方案。
- 确实无法完成的项目允许成为明确记录的残留/延期清理项，不因为这些例外强制回滚已成功的卸载部分。

需要区分的层：

| 层 | 处理原则 |
|---|---|
| SCM 服务与运行代码 | 尽量停止并移除所有产品实例；用户离线本身不必然阻止机器级服务删除，不能据此一概跳过 |
| 每用户 carrier MSI 注册 | 使用合法的 MSI 维护上下文；无法取得必要用户上下文时记录待清理，不手工删除 Installer 注册表/缓存来冒充卸载 |
| VA profile、锁定文件和临时状态 | 能安全清理就清理；仍被占用或状态不明确时保留并报告，允许后续重试 |
| 业务数据 | 是否保留或彻底删除仍按 Q07 决定，不因全机清服务就自动删除所有用户设置 |

实现仍应做到：

- 区分“主程序已卸载”与“全部产品痕迹已清理”，有残留时不显示全机完全清理成功。
- 记录残留所属 owner、资源、实际错误及是否仍运行，提供可诊断、可重试的处理路径。
- 只处理经身份和路径验证的产品资源，不误删其他软件、真实用户账户/profile 或应保留的数据。
- 保持失败状态可恢复，不通过强制卸载 hive、放宽权限或破坏仍在使用的实例来追求表面清空。

本轮 Demo 验证的是 B 在自己的上下文卸载且 A 不受影响；上述全机 best-effort 清理仍需产品集成和测试。
不过，全用户/离线用户“一次性零残留”不再是本方案必须先满足的架构门槛。

评审结论：**Q06 已确认并关闭；允许受控、可见的清理残留，不将其作为方案 blocker。**

## Q07：哪些数据要保留，哪些可以清除？（已决定）

### 迁移完成后是否需要保留旧源文件？

**2026-09-23 评审结论：迁移成功后直接删除旧文件，不新增备份保留周期；其余数据策略亦已同意，Q07 关闭。**

这里删除的是旧的用户可写配置文件，不是已经迁移到 protected store 的有效数据。
已确认的目标时序：

```text
module 验证并生成完整迁移结果
→ service 持久化提交目标数据及初始化状态
→ module 确认提交成功
→ module 在原用户上下文删除本次迁移的旧源文件
```

不能在请求刚发出、尚未确认提交结果时删除源文件，也不能只因旧目录存在就递归删除整个目录。
删除需绑定本次已迁移的源对象/版本，避免误删迁移期间被其他进程替换或重新编辑的数据。
用户已经选择“不允许部分迁移”（Q05），所以整次迁移失败时必须保留旧源文件。

这不需要 retention 定时器，但仍需处理删除失败或两步之间发生崩溃：
保留已成功提交的 protected 数据及初始化状态，明确报告“迁移成功、旧文件清理未完成”，
通过现有重试/下次模块初始化路径重试清理；不能因删源失败重新迁移、回滚有效数据或启用旧路径 fallback。
受保护存储与旧源文件不在一个文件系统事务里，正常立即删除不等于可以省去失败处理。

删除后不承诺旧版 PowerToys 能从原路径直接找回这些设置；
若以后需要向旧版回退，应单独考虑显式导出，而不是自动复活旧文件。

### 当前范围：ACL 保护，不引入数据加密

**2026-09-23 澄清：当前 Workspaces 设置保护方案没有新增数据加密需求，
通过文件 ACL 与 service 的访问授权管理读写权限，不依赖 VA profile 中的解密密钥。**

此前“保留数据依赖 VA profile 密钥”的例子只是未来若采用 DPAPI 等加密时的条件性提醒，
不适用于当前范围，从本次待决问题中移除；不因此增加加密、密钥保留或密钥生命周期机制。

代码更新的签名、CMS 和哈希验证用于验证发布来源与完整性，不是设置数据加密，
这些已有安全机制仍保留。若将来某模块实际需要保存密码、token 等秘密，再单独评估，
不能将未来可能的需求当成当前设计依赖。

卸载若选择保留业务设置，仍须保留数据和必要的受保护初始化状态，
让重装后的合法访问恢复，避免重新导入旧配置；这与保存解密密钥无关。

### 其余已确认的数据策略

- 普通卸载默认保留业务设置；“彻底删除我的数据”必须显式选择。
- 重新安装不能把保留数据当作首次初始化，也不能恢复较旧的 legacy 文件覆盖它。
- 支持用户经 module 导出/导入；导入仍需 validation，不把导出文件直接作为受保护存储使用。

Demo 的 `Clean-Demo` 用于删除测试安装痕迹，不能直接作为生产数据保留策略。

评审结论：**Q07 已确认并关闭：迁移后删除旧源文件；普通卸载保留业务数据及初始化状态，彻底删除显式选择；支持经 module 校验的导入/导出，不引入设置数据加密。**

## Q08：异常修复与重启的产品边界（已决定）

**2026-09-23 评审结论：同意以下建议，作为生产设计要求。**

| 场景 | 已确认要求 |
|---|---|
| 正常更新已有实例的代码 | 不新增 UAC，不要求 Windows 重启；允许短暂服务维护窗口 |
| Bootstrap 损坏、授权边界/服务配置需要修复 | 允许明确的管理员修复流程，不能无限重试或静默降级 |
| 最终卸载时 profile 被系统占用 | 可以明确记录待清理状态并要求重启后完成，但不能把未完成状态显示成完全清理成功 |

这不意味着照搬 Demo 的错误码映射。产品需要判断真实失败原因，保证可恢复，
并向用户区分“功能/服务已卸载”与“profile/缓存仍待清理”。

评审结论：**Q08 已确认并关闭；常规更新与异常修复/最终清理分别处理，具体恢复机制和 UX 仍待实现与验证。**

## Q09：首个生产版本的业务范围（已决定：仅 Workspaces）

**2026-09-23 评审结论：首个生产版本先只做 Workspaces，不在同一版本迁移所有模块的设置。**

底层服务保持通用，不因首期只接入 Workspaces 而加入 Workspaces 专属业务 validation。
其他模块不纳入首期迁移范围；后续接入时可复用已有用户实例，
各自拥有独立的目标授权、初始化状态、schema 和 migration 规则。
数据迁移不等于再次创建 SCM 服务；但新增受保护授权策略可能需要单独的维护流程。

评审结论：**Q09 已确认并关闭；首期业务接入仅限 Workspaces。**

## Q10：服务直接验证原始 MSI，再取得更新内容？（后续独立验证候选）

**2026-09-24 记录：先列入 open questions，后续再决定是否开展独立验证；尚未批准替换当前更新路径。**

### 当前路径与候选路径

当前实现将 Bootstrap、Runtime、manifest/catalog 及其 detached CMS 签名嵌入 carrier MSI。
服务收到的更新输入是已提取的文件集合；服务独立验证清单来源、文件 hash、版本和调用方权限，
不依赖“调用者声称这些文件来自某个已签名 MSI”。

候选路径是：

```text
原 owner 提交对应版本的原始 carrier MSI
→ 服务取得不可被调用者替换的同一份 MSI 快照，并保持必要的文件/目录句柄
→ 验证该 MSI 的签名信任、PowerToys carrier 产品身份、架构和版本
→ 只读取得该 MSI 内固定白名单的 Binary 流
→ 校验提取结果及授权清单，进入已有 prepare / commit / rollback 流程
```

目标是评估：能否以已验证 MSI 作为更新内容的真实性凭证，减少重复签名/验证机制，
同时保持普通更新无新增 UAC、每用户 VA 隔离及同一份字节的验证与使用。
这不是改用 MSIX、让 VA 安装 MSI，或增加常驻 SYSTEM updater。
它也不自动解决发布者信任或证书轮换；MSI 的可信来源仍必须正确验证。

### 独立验证必须回答的问题

| 验证点 | 必须保持的边界 / 需要取得的证据 |
|---|---|
| 验证与读取是否为同一份内容 | 防止校验后替换 MSI、父目录重命名、reparse/hardlink 和 TOCTOU；若 MSI API 按路径重新打开，须证明读取仍绑定同一对象，不能只锁一次然后信任原路径 |
| VA 如何读取 owner 的 MSI | 验证真实 owner、会话和受限读取上下文；不能为了读取而给 VA 开放整个用户 profile，也不能借用任意其他用户或高权限令牌 |
| 只读取内容，不执行安装 | 验证可在 VA 下以只读 API 提取固定 Binary 流；禁止运行 CustomAction、安装脚本或嵌套 MSI 事务，不调用 `MsiInstallProduct` 代替提取 |
| 来源与产品绑定 | 签名有效之外还须验证固定 carrier 产品族、版本、架构和允许的结构；其他厂商 MSI、其他 Microsoft 产品或仅名称相同的包不能通过 |
| 文件和清单处理 | 固定资源名/目标映射，拒绝缺失、重复、额外重定向与超限输入；目标路径由服务控制，不接受包内或调用者提供的任意写入位置 |
| catalog 如何持续作为授权依据 | 验证初始预配、旧/新版本维护调用者认证、普通数据 caller、跨进程 peer 验证及回滚所用的 catalog；改变更新入口不等于所有可独立传递的 catalog 签名都可删除 |
| 原始 MSI 不再可用后如何工作 | 断开源路径、清理缓存或重启后，已提交实例仍须可验证其活动代码/授权清单；明确受保护证据的持久化、生命周期和恢复方式 |
| 更新事务是否仍可恢复 | 验证 prepare/commit 中断、已提交但 MSI 未完成、并发更新、反降级、保留旧版本用于回滚及 A/B 用户互不影响 |
| 支持范围与代价 | 覆盖 x64/ARM64、受支持 Windows、离线/证书过期或吊销、OTS、per-user/per-machine；记录解析面、性能和实现复杂度，不能只以减少 CMS 文件数判断更优 |

最小验收包括：正常 MSI 接受；文件篡改、自建信任根/伪造发布者、错误产品/架构、
降级、跨 owner 和替换竞态拒绝；升级中断可恢复；重启与源 MSI 删除后仍可运行；
不同有效发布证书的处理与所选信任策略一致，不引入手工叶子证书清单作为默认前提。

### 本项的范围与退出条件

- 如决定开展，放在独立 prototype/worktree 中验证，不直接替换当前生产集成分支。
- 输出实际通过/拒绝证据、与当前提取文件路径的安全边界对照，以及实现/维护成本结论。
- 验证后再决定保留当前路径还是采用候选路径；没有验证结果前，不删除现有 manifest/catalog 的真实性检查。
- **本次只记录问题，没有决定采用该路径，也没有启动实验或修改产品代码。**

评审状态：**Q10 保持开放，待后续决定是否单独验证；不把它作为当前方案的新增交付前置条件。**
